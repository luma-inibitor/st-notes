Before the findings

What this is, and what it is not

One operator moved a three-week story off Marinara Engine's built-in chat summaries and onto the Long-Term Memory vault, then wrote down everything the system did along the way. This document collects the result: 83 findings, each one traced either to a symbol in the package source or to an artifact captured while running it.

Nobody asked for this. It is unsolicited feedback from a single person's use at a scale the package probably did not anticipate, and it carries the biases of one corpus, one host and one set of settings. It is not a bug report: the two defects that were plainly defects went upstream as issues on their own. It is not a support request either. Nothing here needs an answer, and the maintainer owns every decision about what to act on.

Scope

The review covers the package's review, apply, diagnostic and error surfaces, its extraction and projection pipeline, and its retrieval and injection path as far as the prompt. It reads the engine wherever engine behaviour decided what the package could do, and it marks those findings so the maintainer can hand them off rather than absorb them.

Six things went unexamined. Lorebook interop, the world-state agent, reconciliation between roleplay time and wall-clock time, multi-persona setups, and group chats never entered the migration, so this review says nothing about them. The sixth is retrieval quality: the findings describe the plumbing that selects and injects memories, not whether the memories it picked were the right ones. Judging that needs a working vector lane, and this host never had one.

How to read a finding

Every finding carries four fields. Severity, evidence grade and effort are independent of one another, so a critical finding can be a small fix and a low-severity one can be a large one.

FieldValuesWhat each value means
Severitycritical · high · medium · low Critical marks a really bad bug or a failure of fundamental functionality. High marks an interface that lies to the user, or a constraint most people hit. Medium marks something workaroundable through the API, misleading rather than incorrect, or a constraint only a power user reaches. Low marks something better prompting fixes, something that may be model-dependent, or a clunky interface a user surmounts by poking around. The rubric is published so anyone can re-grade a row and see where the disagreement sits.
Evidence gradesource · observed · measured · reported Source means someone read the behaviour in the code at a cited symbol. Observed means it happened during the migration and left an artifact. Measured means a number came out of analysis rather than out of the source. Reported means the operator described it and the underlying mechanism is confirmed elsewhere. Sixty-two of the 83 findings are graded source.
Effortsmall · medium · large A rough read of how much the fix disturbs, from wiring an existing helper through to changing a data model. These are estimates from outside the project, and the maintainer will correct several of them.
Bug tagpresent or absent Separates behaviour nobody intended from a design tradeoff someone chose. Fifteen findings carry it. The rest describe decisions that are defensible and still produce a bad outcome at this scale, which is a different conversation from a defect.

One note on naming

The corpus is a private story, so every character and scene name in this document is a neutral alias, applied consistently. Where an example needs a person, it names Wren. Counts, identifier shapes and mechanics stay exactly as they occurred, because those are the evidence: when a row reports two note ids for one subject, the two ids really did exist and really did split that subject's history in half.

The run

What the operator actually did

These 83 findings are the ones a migration of this shape surfaces. A different corpus would have surfaced different ones, so here is the run that produced them, in the order it happened.

The starting position was one continuous story told across ten chats, four of them conversation branches and six roleplay. The engine's two summary subsystems do not know about each other, so the operator had been running a 38 KB script to backfill summaries and character memories in both directions, revising it per chat across several engine versions. By the time this began, summaries occupied 71,635 tokens of context, and one scene chat alone carried 30,719. That is what the vault was supposed to replace.

Planning the migration required reading the package source, because the pipeline runs on seven nouns and the product defines none of them anywhere a user can reach. Understanding the current state required more: no view enumerates chats, summary coverage, connections, embedding health or card leakage, so the operator wrote a 503-line read-only diagnostic to produce one. It immediately found three things the product had never mentioned: the story spanned ten chats rather than the five the operator believed, two scene chats carried conflicting backfills of the same history, and concluded scenes had been writing global memory entries onto character cards that then leaked into every chat using those cards.

The next probe killed the vector lane. The capability embedding host is hard-wired to a local ONNX embedder, whose Linux binaries link against glibc while Termux is bionic, so the binding never loads. Rebuild still reported success and index health still read healthy while the embedded chunk count sat at zero. Establishing that took a dedicated 178-line probe script.

Moving 97 cleaned entries into the vault, extracting them and rewiring five live chats took a 1,981-line orchestrator with 22 subcommands across nine steps, because none of those steps is bulk-addressable through the interface. Extraction then failed four ways in sequence: the engine's 300s outbound timeout killed long batches, a run with no progress channel sat silent for minutes and read as a hang, one oversized entry threw ltm_model_output_truncated and discarded the whole response, and the operator's own resume cursor advanced past failed batches.

Then the worst one. Recall selected seven chunks at 99% relevance and the engine discarded all seven, because a preset that assembles the prompt drops agent output unless it carries a marker section. One preset was shared by four roleplay chats, so one missing section disabled memory across four chats at once. Every layer reported success. The debug log said recall had worked, which from the package's point of view was true.

Chasing why the vault felt thin turned up 200 auto-rejected candidates reachable through an endpoint, 132 of them for untrusted subjects. The operator redid the extraction from cleaned sources, which needed a lint pass, a briefing document for a second agent, and a vault-wipe command that also cleared checkpoints. Reviewing the result meant 97 drafts, 1,142 claims and 161 notes, one draft at a time, against a story organised by subject: seeing 40 claims about one person meant visiting 40 drafts. That produced a 2,545-line review workbench, served over a local HTTP server because an Android content:// URI breaks relative fetches from a file. Applying it hit two hard walls with no prior warning, the 30-keyword cap and the 20,000-character section cap, the second of which failed 35 drafts with 35 identical messages that name neither the note nor the section.

Before the complaints

What the architecture already gets right

Eighty-three findings follow, and nearly all of them describe a layer that reports what the system is doing rather than the system itself. That distinction matters for deciding what to change, so here is the part worth protecting. Several of these decisions are why a migration of this size was possible at all, and two of them are better than what comparable systems ship.

Information model

Typed notes with per-type semantics

Character, relationship, world, thread, timeline event, tone and anchor, each with its own rule about which sections accumulate and which supersede. This is a real model rather than a bag of text, and it is what makes grouping a review queue by subject possible at all.

isAdditiveLtmSection() · ltmNoteType

Provenance

Every claim can be traced to the text that produced it

Each mutation cites its source note, and each note links back through extracted_from. When something looked wrong during the migration, tracing it to the exact summary entry that produced it always worked. Very few systems in this space do this, and none of the diagnosis behind these findings would have been tractable without it.

evidence refs · extracted_from links

Failure mode

Conflicts get recorded, not resolved

When two claims disagree about a superseding value, the projector writes a conflict instead of letting one silently win. The resulting failure mode is that a person has to decide, which is the correct failure mode for a memory system. The gap is that nothing surfaces the conflict for deciding, not that the engine mishandles it.

draft-projector.ts · conflicts[]

Best in the apply path

A partial selection pulls in what it depends on

Accepting a subset quietly includes the create_note that subset needs and the timeline events its change claims ground against. Partial review is therefore safe by default. This is the best-designed thing in the apply path, and the finding attached to it concerns only the asymmetry between undecided and rejected.

filterAutoApplyDependencies() · applyInner()

Resumability

Partial accept returns the draft to pending

A half-finished review costs nothing and picks up where it stopped, because the apply path rewrites the draft to exactly the unselected set. Incremental review across several sittings rests entirely on this one behaviour.

applyInner() · updateDraftStatusUnlocked()

More than most offer

Edit before accept, re-validated server side

The accept route takes fully edited mutations, re-validates them, and refuses to let a caller change the kind or claim kind. Edit-before-accept is exactly the right primitive for a review queue. The finding against it is that the control carries no label, not that the capability is missing.

editedMutations on the accept route

Anticipated the question

Rejections carry a recovery target

A dropped candidate records its reason code, a human message, the source snippet, and a recovery object naming the note type, note id, section key and status it would have written to. Someone built this expecting to be asked why a claim vanished.

addRejectedSuggestions() · recovery{}

Verification

The injection count is checked against the real prompt

The dispatch record only counts an injection after confirming the artifact actually appears in the messages that went out. The number is trustworthy when it moves. Its problem is that it never moves to zero.

Before the drawings

What the package is allowed to do

These proposals are scoped to what a capability package can build without an engine change, because the package maintainer may not own the engine. Four facts from the source decide the shape of everything below, and one of them costs a proposal outright.

Generous

Most of this is the package's own code

It registers arbitrary routes under its own prefix, owns its storage directory and its schema, gets a revision-checked document store, and can call both a language model and an embedding model. Every derived signal, the facet engine, apply preview, restore points and compaction are all in reach.

capability-module-runtime.service.ts · activateOne

Constraint

Nothing can be pushed to the client

There is no event channel of any kind: no server-sent events helper, no websocket, no invalidation signal. Every live surface here polls a route, which is exactly what the package already does for its debug log.

no EventSource or WebSocket anywhere in packages/client/src

Constraint

A new route means a restart

Route paths cannot appear after the server is listening, so adding one is a release decision rather than a runtime one. Frames that need a new route are marked, because that changes how they ship, not whether they can.

capability-route-registration.service.ts · createRouteCollector

Costs a proposal

Nothing can render in the transcript

The conversation mounts are chosen by a package's declared kind, which this package does not have, and they sit outside the message list regardless. Message content is sanitised through a fixed allowlist that strips capability elements. So the recall report cannot sit beside the message it explains.

ConversationView.tsx · ChatMessage.tsx · sanitizeChatHtml

The proposals

Six journeys

Each is drawn in several states, from the moment a person wants something to the moment they have it. Click the state chips to step through; desktop and phone move together. Every state carries a feasibility mark and the findings it answers.

1

First run

Switch it on and reach visible proof it worked. Today this journey ends in nothing recalled, so the failure is drawn before the fix is.

2

Import and extract

Narrow a large library, pick the material, confirm who the run may write about, and read what it cost without opening the review queue to find out.

3

Curate

Eight hundred claims, decided in slices rather than one at a time. The unit of work is a composed cross-section, not a draft.

4

Browse and correct

Find the memory that is wrong, then fix it. The same facet engine as review, over what is stored rather than what is proposed.

5

Why didn't it remember

The report cannot sit beside the message it explains, so it is built where the package does have surfaces, and it keeps a history worth walking back through.

6

Keep it healthy

Caps that read as a gradient rather than a wall, and a compaction pass that shows what it would remove before it removes it.

C. Naming

The corpus is a private roleplay, so every character and scene name carries one consistent neutral alias throughout, and raw chat identifiers drop out rather than receiving an alias. Counts, identifier shapes and mechanics stand unchanged, because those carry the evidence. Citations name a file and a symbol instead of a line number, since line numbers rot across releases and a maintainer reading this later would land somewhere unrelated. Error strings appear verbatim, because those stay greppable.
